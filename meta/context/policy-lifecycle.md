# Policy lifecycle — from Opportunity to Renewal

**Last verified:** 2026-09-01 · **Owner:** unassigned

## What this is

The path a piece of business takes from a confirmed insurance need through placement, issuance, mid-term change, and renewal. Source: `IBMS_Full_Scope_Context_Document.docx` Parts 3.2–3.6 and 3.9. Claims are handled separately — see `meta/context/claims-lifecycle.md`.

## The shapes

```
Opportunity.status:
  Needs Confirmed → RFQ Issued → Quotes Received → Comparison Built →
  Recommendation Drafted → (Compliance Check) → Sent to Client →
  Client Decision → Placement | Renegotiate | Closed-Lost

Policy.status (post-placement):
  Placement Confirmed → Issued (received from insurer) → Checking In Progress →
  Discrepancy | Verified → Delivered → Active

Endorsement/Cancellation.status:
  Requested → Submitted to Insurer → Insurer Confirmed →
  Financial Adjustment Calculated → (Refund Approval if applicable) →
  Applied → Client Notified

RenewalCase.status:
  Renewal Due → In Progress → Quotes Obtained → Recommended →
  Client Decision → Renewed | Lapsed | Cancelled
```

Client decision branches at two points and each routes differently: **Accept as recommended / Reject / Request further negotiation / Request alternative options / Request price reduction / Request coverage increase** — each is a distinct next step (Placement, RFQ closed, or renewed Negotiation), not a single generic "declined" state.

## The rules that aren't obvious

- **Policy Checking must be performed by someone other than whoever requested/placed the cover — a hard system rule, not best practice** (Part 3.4). See `meta/lex/maker-checker-segregation.md`. A discrepancy (e.g., requested limit JOD 5,000,000, issued limit JOD 3,000,000) puts the policy in `Discrepancy — Correction Requested` and blocks Delivery until resolved; this is logged as a Professional Indemnity risk event, not silently corrected and moved on.

  - **The `DISCREPANCY` state IS the Delivery block — so driving a Policy to it is a control action, not a best-effort side effect** (`ibms-app` Part C #20, `PolicyCheckingService`). The check records its result authoritatively (the `PolicyChecking` row + the linked PI risk event, created in one transaction so "a discrepancy is recorded" ⟺ "a PI event exists"), then walks the parent `Policy` `(ISSUED | DISCREPANCY) → CHECKING_IN_PROGRESS → (VERIFIED | DISCREPANCY)` through the workflow engine. That walk is best-effort **for a clean (`VERIFIED`) outcome** — a clean result that can't be applied because the policy moved on is harmless. It is **NOT** best-effort for a **discrepancy** outcome: if a concurrent divergent check verified the policy first and the transition map has no edge back onto the checking path, a swallowed failure would leave the policy `VERIFIED` with `discrepancyFound = true` and its PI event logged, yet Delivery unblocked — the exact PI-claim failure mode Process 20 exists to catch. So an unappliable `DISCREPANCY` outcome is a hard error (409), not a logged warn. Generalised: **when a best-effort status walk's terminal state is itself a safety gate, an unappliable outcome must fail loudly, not be logged and swallowed.** The residual — two officers checking one policy near-simultaneously with divergent transcriptions can still race on `PolicyChecking.discrepancyFound` itself (last-write-wins upsert) — needs per-policy serialisation of the check to fully close; `ibms-app` product decision (Part C #20), no source document.

  - **`maker-checker-segregation.md`'s table maps `PolicyChecking`'s maker to `placedByUserId` only — but the checker compares against the *issued* schedule, which the *issuing* officer transcribed (Process 19).** Part 3.4's rationale ("undetected mismatch between requested and issued coverage") arguably wants the checker distinct from whoever produced the issued record too. `ibms-app` (Part C #20) enforces `checkedByUserId ≠ issuedByUserId` **app-side** (`assertDifferentActors`) as a stricter-than-lex belt; the DB `CHECK` constraint still only covers `placedByUserId`. A decision is needed on whether the lex row and the `CHECK` should extend to `issuedByUserId`.
- **Comparison is never price alone.** The Quotation Comparison must be built across price + coverage + exclusions + deductibles + limits + insurer quality + service. A submission on a price-only comparison is a controls failure, not a shortcut (Part 3.3 Controls).
- **A Recommendation favoring a materially higher-commission insurer over a comparable/better-value competing offer requires an explicit Conflict of Interest disclosure before it can be sent to the client** (Part 3.3) — this is a system gate, not a documentation afterthought.

  - **What "comparable" and "materially higher" mean, quantified** (`ibms-app` Part C #16, `RecommendationService.detectConflictOfInterest`): a competing quote is **comparable** when its premium is within **10%** of the recommended quote's premium (a much more expensive quote is not an offer the broker realistically passed over); commission is **materially higher** when the recommended insurer's commission rate exceeds the *lowest-rate comparable competitor's* by **≥ 2 percentage points** (absolute, not a ratio). Tie-break among comparable competitors is deterministic: lowest rate → lowest premium → id. A recommended quote with **no captured `commissionRatePercent`** (Process 13) cannot be assessed and is **not** flagged — the check needs the rate. Both the 10% band and the 2 pp threshold are **`ibms-app` product decisions, draft, unsourced** — no CBJ / Part-3.3 / market-practice figure specifies either; a real number should replace them. Competitors are scoped to the recommended quote's **own RFQ line** (a cross-line quote is not a "comparable competing offer"), matching Comparison (#14)'s per-RFQ `ComparisonMatrix`. The gate is re-evaluated against **live** data at send time (a threshold configured, or a comparable competitor quoting, *after* the recommendation was drafted still blocks the send) — a snapshot taken only at draft would be bypassable by event ordering, i.e. procedural not structural (`meta/lex/maker-checker-segregation.md`). `maker-checker-segregation.md`'s covered-actions table has no Recommendation-drafter → COI-acknowledger row; `ibms-app` gates it with `assertDifferentActors` (acknowledger ≠ drafter) and grants `conflict-of-interest.disclose` to both Placement and Compliance for now — a row in that table would let the grant narrow to Compliance-only.
- **Cover Notes/Binders are a real interim state with a tracked expiry**, used when urgent cover is needed before full policy issuance — model this explicitly, don't fake it as an early Policy row.
- **Negative endorsements (return premium) trigger the Refund Management workflow**, which is maker/checker-gated by value threshold — the officer who raises the endorsement never self-approves the refund (Part 3.5).
- **Cancellation always computes a Commission Reversal tied to the same premium adjustment** — the two numbers must move together; a cancellation without a matching commission reversal is a broker overpayment exposure waiting to surface (Part 3.5 Risks).

  - **The refund value threshold and the short-period return figure are drafted, unsourced `ibms-app` product decisions** (backlog Part C #22, `endorsement.config.ts`): `REFUND_APPROVAL_THRESHOLD_JOD` (the value at/above which a return-premium `Refund` needs a distinct approver before the endorsement can be APPLIED — below it the refund is auto-cleared single-actor) and `SHORT_PERIOD_CLIENT_RETURN_PERCENT` (a short-period cancellation returns the client this % of the pro-rata figure — the rest is an early-cancellation penalty the insurer retains). No CBJ / Part-3.5 / market figure specifies either; a real Finance approval matrix (narrative Process 37/40) belongs to a Finance-config surface that does not exist yet, and there is no short-period scale table (by months elapsed). Same "drafted constant pending a real number" status as #16's 10% comparable band / 2 pp commission threshold. `pro_rata` cancellation itself is exact (`issuedPremium × unexpiredDays / totalPolicyDays`).

  - **The maker/checker gate on an above-threshold refund must be structural at the APPLY write, not only a status.** In `ibms-app` the `Endorsement` status walk is `… → FINANCIAL_ADJUSTMENT_CALCULATED → (REFUND_APPROVAL_PENDING →) APPLIED`, and the `→ REFUND_APPROVAL_PENDING` hop is a *separate, best-effort* transition from the `→ FINANCIAL_ADJUSTMENT_CALCULATED` write. A crash, statement timeout, or a concurrent `apply` call between the two writes can strand the endorsement at `FINANCIAL_ADJUSTMENT_CALCULATED` with an above-threshold `Refund` whose `approvedByUserId` is still null — and the engine map allows `FINANCIAL_ADJUSTMENT_CALCULATED → APPLIED` unconditionally. So the apply path itself must refuse when `refund != null && refundNeedsApproval(refund.amount) && refund.approvedByUserId == null`, regardless of status. Guarding only on `status == 'REFUND_APPROVAL_PENDING'` is procedural, not structural (`meta/lex/maker-checker-segregation.md` § Rationale; `meta/lex/race-safe-invariants.md` — a "has approval happened / is it required?" check read off a separately-written status column is a check-then-act).

  - **At most one in-flight cancellation per policy is a race-safe invariant, not a status check.** The `Policy` stays `ACTIVE` from the moment a cancellation is *requested* until the first one is *APPLIED*, so a plain `policy.status === 'ACTIVE'` guard in "raise a cancellation" lets a second cancellation `Endorsement` be raised (operator picked the wrong `basis` and re-raises; there is no void/withdraw endpoint) and driven independently to APPLIED — minting a **second `Refund` + `CommissionReversal`** for the same policy. `ibms-app` backs it with a partial `UNIQUE` index (`Endorsement_one_live_cancellation_per_policy ON ("policyId") WHERE "changeType" = 'cancellation' AND "status" <> 'CLIENT_NOTIFIED'`, raw SQL — Prisma can't express a two-column partial `UNIQUE` on the mutable `status`), plus a friendly pre-check, plus `P2002 → 409` (`meta/lex/race-safe-invariants.md`). A cancellation reaching terminal `CLIENT_NOTIFIED` drops out of the index, so a later cancellation of a reinstated policy is still possible.

  - **Driving the `Policy` to `CANCELLED` at cancellation-apply is a control action, so it must fail loudly.** Same generalisation as the Policy Checking row below (a best-effort status walk whose terminal state is itself a safety gate must throw on an unappliable outcome, not swallow it): a policy left `ACTIVE` after its cover was cancelled would be picked up by renewal / cross-sell sweeps and would still accept claims. `ibms-app` makes an unappliable `ACTIVE → CANCELLED` a hard 409 (already-`CANCELLED` — a concurrent apply won — is success); the `Endorsement` is already APPLIED and its schedule closed, so a retry of `apply` is re-entrant and just re-attempts the policy transition.

  - **Endorsement / cancellation `effectiveFrom` must fall inside the cover period and no earlier than the current open `PolicySchedule` version.** A backdated value closes that schedule with `effectiveTo < effectiveFrom` and opens a successor that starts before its predecessor, corrupting the "coverage in force at the loss date" resolution a `Claim` depends on. No CBJ/Part figure — an `ibms-app` data-integrity guard (Part C #22).
- **Renewal starts automatically at a configurable lead time before expiry (default 90 days)**, and the Loss Ratio for the expiring period is computed and surfaced *before* the recommendation is drafted — never negotiated blind (Part 3.9). No renewal action within the lead-time window escalates to Customer Retention, not silence.
- **A mid-cycle risk change since the last renewal** (new location, headcount growth) **triggers a fresh Risk Assessment before the renewal RFQ is issued** — a renewal is not automatically a roll-over of the last Risk Assessment.
- **Renewal terms declined or materially worsened by the insurer trigger full re-marketing** (a new RFQ to alternate insurers), not a simple roll-over attempt with the same insurer.
- **An RFQ follow-up threshold lapsing auto-marks the silent insurer's submission `NO_RESPONSE`** — it is not only an alert for a human to action. Each `RFQ` carries a configurable `followUpThresholdDays` (default 9), counted in Jordan business days from each `RFQInsurer.sentAt`; the nightly follow-up sweep (Process 12, Market Placement) stamps the alert *and* advances a still-`SENT`/`VIEWED` submission to `NO_RESPONSE` through the workflow engine. This is a status change by a system actor, so it is race-conditional: an insurer response landing first makes the auto-move a no-op. `NO_RESPONSE` is **not terminal** — a late-responding insurer can still be moved `NO_RESPONSE → QUOTED / DECLINED`. Source: no CBJ/Part-3.3 document specifies the turnaround or the auto-vs-alert choice — the threshold default and the auto-advance are `ibms-app` product decisions (backlog Part C #11–12), draft pending a real market-practice figure.

  - **"Silent" is decided against the `Quotation` table too, not `RFQInsurer.status` alone.** Capturing an insurer's quote (backlog Part C #13, `QuotationService`) writes a `Quotation` row directly and *best-effort* moves the matching `RFQInsurer` `→ QUOTED` — but that transition is logged, never thrown, so a race or a transient failure can leave the submission `SENT`/`VIEWED` while a current `Quotation` for its `(rfqId, insurerId)` already exists. The follow-up sweep therefore **skips any submission that has a current `Quotation`** (in `ibms-app`: `RfqService.runFollowUpScan` calls `RfqRepository.findCurrentQuotationKeys` up front, before the business-day threshold check; the skip is tallied as `FollowUpScanResult.skippedQuoted`) — an insurer that quoted is not silent, even if its status column has not caught up. Generalised: **`RFQInsurer.status` is not the authoritative "has this insurer quoted?" signal — the `Quotation` table is** (`QuotationService` documents the same rule on its own side). Without this guard a genuinely-quoted insurer would be mislabelled `NO_RESPONSE` until someone revises the quote — bounded (`NO_RESPONSE → QUOTED / DECLINED` is legal, and downstream Comparison #14 / Recommendation #16 read the `Quotation` table, not the status column) but the status column would then be wrong. `ibms-app` product decision (Part C #13), no source document.
